Section 1
第 1 节

Two layers: what the harness gives, what the preset builds 两层结构：Harness 给了什么，预设在上面建了什么

DeepSeek Harness is a Cordis composition: every capability is a plugin row. An agent preset is one such file mounted for a single session. RigorQuant ships exactly that — one preset composition plus a bundled skill tree plus one small host plugin — so the entire research framework below is built from harness primitives, with no fork of the harness itself. DeepSeek Harness 是一个 Cordis 组合：每种能力都是一条插件行。Agent 预设就是为单个会话挂载的这样一个文件。RigorQuant 发布的正是它 —— 一份预设组合、一棵随附的技能树、一个小型宿主插件 —— 因此下面整个研究框架完全由 Harness 的基础组件搭建，没有 fork Harness 本身。

Layer 1 — DeepSeek Harness foundation (consumed, never re-implemented) 第 1 层 —— DeepSeek Harness 基座（只消费，不重造）

  • Preset composition rows — persona injection (@deepseek-ai/dsh-persona), shell/filesystem/search tools, background jobs, plan mode, ask-user, todo, web search + fetch. 预设组合行—— 人格注入（@deepseek-ai/dsh-persona）、shell／文件系统／搜索工具、后台任务、计划模式、用户问答、联网搜索与抓取。
  • Skill registry + skill tool — the preset anchors its own skill root at baseUrl, so the operating procedure travels with the preset. 技能注册表 + skill 工具—— 预设把技能根目录锚定在自己的 baseUrl 上，操作规程随预设一起走。
  • Per-role delegation — the same row (@deepseek-ai/dsh-tool-subagent) mounted seven times with different personas, toolFilter.deny lists and maxDepth; spawned children never see the parent conversation (context isolation is harness-enforced). 按角色委派—— 同一行（@deepseek-ai/dsh-tool-subagent）以七种不同人格、不同的 toolFilter.deny 与 maxDepth 挂载七次；派生的子代理永远看不到父会话（上下文隔离由 Harness 强制）。
  • Goal loop — one task-level goal relaunches the orchestrator every round inside the live session. 目标循环—— 单个任务级目标在活会话内每轮重新拉起编排者。
  • Compaction + tool-result pruner — tuned to fire earlier (60% of context window) and retain less (4 KiB per result) because long runs re-send the prefix on every step. 压缩 + 工具结果修剪器—— 调整为更早触发（上下文窗口的 60%）且保留更少（每条结果 4 KiB），因为长运行会在每一步重复发送前缀。
  • Sandbox + approvals — workspace-write file policy; anything beyond it fails closed or asks. This is not hypothetical: it shaped the compute lane (step S4). 沙箱 + 审批—— 文件策略为 workspace-write；越界操作要么失败关闭、要么请求批准。这不是假设：它直接塑造了计算通道（见步骤 S4）。
  • MCP client row — one opt-in lane for the Lean escalation verifier, command pinned. MCP 客户端行—— 一条可选的 Lean 升级验证通道，命令被固定版本。
  • Host plugins + settings + Slots — the role-model router listens on the agent/request waterfall; its Settings card renders in the Plugins tab. 宿主插件 + 设置 + 槽位—— 角色模型路由器监听 agent/request 瀑布流；其设置卡片渲染在插件页签里。

Layer 2 — what dsh-rigorquant adds第 2 层 —— dsh-rigorquant 增加的部分

  • A root-orchestrator persona with four non-negotiable constraints (producer ≠ checker; counterexample-only elimination; seeds always recorded; no handwaved load-bearing claims) and precise, non-marketed definitions of “isolated” and “unattended”. 根编排者人格，含四条不可协商约束（生产者≠检查者；只凭反例淘汰；随机运行必记种子；不许空谈承重命题），并对「隔离」与「无人值守」给出精确、不掺水的定义。
  • The rigorquant skill — the operating procedure: Steps 0–2b, the round loop, the stage order, the check battery, escalation triggers, anti-patterns, lifecycle. rigorquant 技能—— 操作规程：步骤 0–2b、轮循环、阶段顺序、检验组、升级触发条件、反模式清单、生命周期。
  • Seven role tools out of one row — explorer / OffGridThinker(off-grid, blind) / DoubleChecker(blind) / adversary / lit-line / lit-adversary / doc-adversary, each a separate model-facing tool so producer ≠ checker is enforced by which tool runs, not by asking nicely. 一行变七个角色工具—— 探索者／离网思考者（离网、盲态）／双重复核（盲态）／对抗者／文献线代理／文献对抗者／文档对抗者。每个都是独立的模型可见工具，「生产者≠检查者」因此由调用哪个工具来强制，而不是靠口头请求。
  • The meta-validator rq_check.py + JSON Schemas it loads itself (“one validator, one schema”) — the honesty boundary that reads the audit record, never study.json. 元校验器 rq_check.py 及其自行加载的 JSON Schema（「一份校验器、一份 schema」）—— 这是诚实性边界：只读审计记录，绝不读 study.json 自证。
  • The study convention — one self-contained folder layout everywhere, durable deliverables committed, all scratch gitignored under interim/. 研究目录约定—— 到处一致的独立目录结构：耐久交付物入库提交，全部草稿放进被 gitignore 的 interim/。
  • A test suite that includes a forged study which must FAIL — the honesty gate is itself tested. 一套包含「伪造研究必须 FAIL」的测试—— 诚实闸门本身也被测试。

S2

Step 0 — Intake: promise narrowly, verify everything, pin the rulers 步骤 0 —— 立项：窄承诺、全验证、钉死量尺

Foundation基座层

Filesystem tools write study.json; ask_user_question is available but rationed (at most ONE question at intake, none on resume); bash hashes the schema and validator for intake pins. 文件系统工具写入 study.json；ask_user_question 可用但限量（立项至多问一个问题，恢复时零提问）；bash 为 intake 钉扎计算 schema 与校验器的哈希。

Framework框架层

Intake records: the original question verbatim as broad_criterion (never re-scoped to whatever turns out provable); sub-problems each with a success criterion; a mandatory coverage gate — at least one generalization sub-problem carrying the broad claim and at least one domain-scale sub-problem; hand-checkable simplified cases; seeds and tolerances; intake_pins (SHA-256 of the schema and validator in effect); declared deliverables. Then the meta-validator runs — and is expected to fail at first. 立项记录：原始问题逐字存为 broad_criterion（绝不缩水成碰巧可证的那一部分）；每个子问题各带成功判据；强制覆盖闸—— 至少一个承载大主张的 generalization 子问题、至少一个 domain-scale 子问题；手算可验的简化情形；种子与容差；intake_pins（当时生效的 schema 与校验器的 SHA-256）；声明的交付物。然后跑元校验器 —— 并且预期它先失败。

S3

Step 1 — Study workspace: detect first, ask once, never re-ask 步骤 1 —— 研究工作区：先探测、问一次、永不重问

Foundation基座层

The goal tool: the orchestrator creates one task-level goal and the harness's goal-round driver relaunches it every round while the session stays alive. Crossing a session boundary disarms it; one human turn (“continue”) re-arms it. That is the precise meaning of “unattended” here. 目标工具：编排者创建单个任务级目标，Harness 的目标轮驱动器在会话存活期间每轮重新拉起它。跨会话边界会使之解除武装；人类一句「continue」即可重新上膛。这就是本项目「无人值守」的精确含义。

Framework框架层

Study-root resolution is detection-first: walk up looking for study.json but never past the git root; reject symlinks; studies/*/study.json roster means multi-study Mode B. A new study asks exactly one question (mode + slug), mints YYYYMMDD_<topic>, creates the layout, a .lock naming the live run, and appends-only journal.md from then on. 研究根目录解析是探测优先：向上找 study.json 但绝不越过 git 根；拒绝符号链接；存在 studies/*/study.json 即多研究的 Mode B。新建研究只问一个问题（模式＋slug），铸造 YYYYMMDD_<topic> 形式的标识，创建目录结构、写上标明活动运行的 .lock，此后 journal.md 只增不改。

S8

Round loop ③ — Adversary: routes die by counterexample or not at all 轮循环 ③ —— 对抗审计：路线只能死于反例，否则不死

Foundation基座层

A different tool runs the checking role — that is the entire enforcement of producer ≠ checker. The adversary keeps bash and web on purpose: it re-runs scripts, re-retrieves sources, and verifies hashes itself. S10

Framework — five stages, in order, per sub-problem 框架层 —— 五个阶段，按序，逐子问题

1 · Reference-case gate — the four-part check battery on simplified cases: (A) closed-form equality, (B) exact invariants, (C) analytic bounds, (D) statistical hardening (fixed seed, LLN shrinking ≈ C/√N).
